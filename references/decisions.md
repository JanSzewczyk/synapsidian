# Synapsidian plugin: decision log

Running record of the requirements interview. Each entry: the decision, and why.
Reference project: [eugeniughelbur/obsidian-second-brain](https://github.com/eugeniughelbur/obsidian-second-brain) (v0.17.0).

| # | Topic | Decision | Notes |
|---|---|---|---|
| D5 | Note format | **Hybrid** | Human-readable body. Frontmatter carries `type`, `tags`, links and a one-sentence `summary` that feeds the index and recall. Date stamps (`as of`) only on facts that go stale. No `## For future agent` preamble. |

| D83 | Embeddings after the measurement (2026-10-14) | **Not built** | Real-vault set (24 questions, private): English queries, as `find` sends them after translating, reached recall@5 0.938 and recall@1 0.812; the gate (+10 points) was unreachable with at most 6.2 points left. The one miss was lexical and was fixed instead: "1:1" / "1-1" / "one on one" fold to one token, and descriptive frontmatter (role, relationship, kind, project, app...) is searched as a `properties` field. After the fix: recall@5 1.0, recall@1 0.875, synthetic set unchanged (1.0 / 0.95). Raw Polish queries score 0.25, which is why `find` translates first. Re-measure with `synapsidian find --eval <vault>/.git/synapsidian/search-eval.jsonl --all` when the vault has grown (hundreds of notes) or misses start showing up. |
| D84 | How a source counts as integrated (2026-10-14, ZAD-8) | **Explicit `integrated` date** on source notes | Ingest sets `integrated` together with `summary` and `tags` in step 5, after the notes are updated; absent means the run hasn't finished. An empty `summary` was ambiguous (a summary says nothing about whether the notes were updated). `Sources.base` gets a *To integrate* view filtered on `not: file.hasProperty("integrated")` (`date.isEmpty()` returns false per the Bases docs, so `hasProperty` is the reliable test) and one view per `source_kind` (ZAD-7). Existing sources were backfilled with the date they were integrated. |
| D85 | Obsidian Git next to synapsidian's commits (2026-10-14, ZAD-2 review) | **Detect and report, don't block** | Obsidian Git's timer commits every changed file and doesn't know synapsidian's lock, so it can take a run's file before the run commits (seen 2026-10-13/14: a review's archive left `Welcome.md`'s deletion uncommitted until `vault backup` took it). `synapsidian commit` now adds the old path of any `Archive/...` note itself and reports listed files whose latest commit is a non-synapsidian one from the last 3 hours as `swept`; skills tell the user which commit holds the change. Blocking the plugin isn't possible from outside Obsidian. The setup reference also recommends the Web Clipper with a `synapsidian capture` template (link plus selection into `Inbox/`, ingested by `/synapsidian:save inbox`). |
| D86 | Setup verifies the session capture; work options have no defaults (2026-10-14) | **`check` reports an `automation` block and gates `ready`; `selftest` drives the hooks; `github_repo`, `jira_project`, `work_repo_path` default to empty** | A vault could be `ready` while nothing captured sessions (no uv where hooks look, no `jq`/`python3` for `session-end.sh`, hooks missing) and the user would learn it only when the evening run found an empty queue. `selftest` feeds a fake SessionEnd to a throwaway vault, reads the row back through uv and runs the SessionStart brief on the real vault, so the real queue is never touched. Scheduled tasks stay with `/synapsidian:schedule` (they are an MCP surface, not readable from scripts). The three work options carried the author's own repo, Jira key and path as defaults, which silently pointed other users at someone else's data (and an empty `work_repo_path` would have scanned the cwd); now `None` means skip that source. |
| D87 | Sessions open for days (2026-10-14) | **Marks are watermarks; pending also scans recent transcripts** | The queue gets a row only on SessionEnd, dated the day the session ended, and a mark closed a (session, day) for good. A desktop session resumed across days (this one, 13-14.10) lost its work after the 13.10 17:36 mark and would have had 14.10 logged only if it ended that same day. Now a (session, day) is pending when it was queued and never marked, or when its transcript has records that day after the last mark; transcripts modified in the last 14 days are scanned besides the queue (days before the first queued day are skipped: Notion logged them). `digest --date` shows only records after the last mark and prints `mark with: --date D --until <digest time>`, so work done while the evening runs stays pending. Closing messages are flattened to one line so their headings don't look like sessions. Rehearsed on a copy of the vault: both days logged, one commit each, nothing pending after. The Notion devlog-rollup reads the same SessionEnd queue and keeps this gap. |
| D88 | Universality (2026-10-14) | **The plugin is user-agnostic; work features are an optional layer** | Supersedes D2's scope for the plugin (D2 still describes the author's own vault). The core (layout, schema, notes, tasks, save, find, ingest, research, think, evening, review) must fit a personal vault with no job context. Work-tied features (1:1s, stand-up, Jira, PRs, Slack/email commitments, architect) are gated on `userConfig` / `About.md` and off when empty (D86 pattern); the target is a separate `synapsidian-work` plugin in the same marketplace. No author-specific names, keys, apps, cadences, paths or Polish strings in anything read at runtime. Narrows D81 (the three monorepo apps) to the author's configuration, not the plugin's. Rules in `CLAUDE.md`. |
| D89 | Scheduled tasks' folder (2026-10-14, 0.11.2) | **The vault is every synapsidian task's folder; the vault ignores `.claude/`** | A desktop scheduled task takes the folder of the session that created it, and the scheduled-tasks tools can't change it.
